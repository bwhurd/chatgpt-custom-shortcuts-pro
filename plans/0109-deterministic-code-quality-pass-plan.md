# Plan 0109: Audit and improve consequential code quality

## Outcome and decision rules

- [ ] Audit maintained code for incorrect outcomes, unnecessary recurring work, and maintenance hazards; implement justified repairs and prove the result. Execute with GPT-6-Luna, Max reasoning, through `plans/luna-deterministic-code-quality-pass-thread-prompt.md`.
- [ ] Prioritize lost/corrupted settings, false success, wrong or duplicate actions, stale asynchronous results, accumulating background work, and checks that report false passes. Then address costly repeated work and duplicated policy that demonstrably causes drift. Function length, nesting counts, naming preferences, and lint volume are search clues, never sufficient findings.
- [ ] Admit a repair only with a current reachable path, concrete trigger, observed or statically established problem, expected contract, smallest fix, and a way to distinguish success from the original behavior. A maintenance improvement must identify the duplicated policy or tangled responsibility and a concrete change/error it makes costly; preserving intentionally different behavior is part of its proof.
- [ ] Rank by consequence and frequency/reach first, then evidence confidence, repair risk, and proof cost. State these reasons rather than inventing a numerical score or finding quota. Zero edits in a reviewed area is a valid outcome.
- [ ] Five batches provide a short triage pass followed by three owner-specific audit/repair loops and one final gate. Data/service failures go first because there are concrete current leads. Discovery continues in the owning batches; a complete list of defects is not a prerequisite to the first useful repair.

## Proof and check selection

- [ ] Before a behavioral repair, write the expected observable result and the exact check that will distinguish it from the defect. Run the focused reproduction against unchanged source where feasible, then against the repair. A static-only finding needs an explicit branch/data-flow argument and an honest runtime-unverified label. Passing lint cannot promote it to behaviorally verified.
- [ ] New regression tests must exercise actual shipped functions/handlers, with external boundaries stubbed. Do not copy the algorithm into the fixture. Challenge a meaningful negative case or show the test fails on the original defect; avoid tests that merely assert implementation shape. Existing fixtures extract source text, so update extraction carefully after refactors without substituting copied behavior or weakening assertions.
- [ ] Efficiency proof compares the same workload/input/DOM and preserves outputs while measuring actual operations/resources. Fewer source call sites or fewer lines alone proves no runtime saving. Use controlled counts first; use a small repeatable timing comparison only when counts cannot answer the question. No machine-speed thresholds or new benchmark framework by default.

| Changed contract | Available command / proof choice | What a pass establishes and what still needs proof |
| --- | --- | --- |
| Code/text hygiene | `npm run check` for aggregate acceptance; `./node_modules/.bin/biome.cmd check <changed supported files>` during edits | Syntax/lint/text rules. Fix only clear safe diagnostics; suppress style-only items narrowly per repo rules. These checks do not prove behavior. Record pre-existing failures separately; do not expand scope to make a broad gate green. |
| Settings wiring | `npm run validate:keys` | Static controls/defaults/schema/locale wiring. Use a separate actual-function fixture for migration, data preservation, or cloud outcomes. |
| Popup changes | `npm test` | Popup visual/layout, one toggle persistence round trip, clipping and console checks. It does not establish cloud errors, all settings, concurrent handlers, or native integrations. |
| Shortcut behavior | `npm run test:shortcuts:fast -- --shortcut-action-id <current action ID>` during repair; one unfiltered `npm run test:shortcuts:fast` for final affected source | Controlled dispatch and effects. Verify selected cases actually ran and inspect warnings; exit 0 with zero/partial cases is insufficient. It does not establish today’s live DOM or OS/account effects. Shared dispatch changes require broader affected coverage. |
| Existing owner fixtures | For example `node tests/topbar-to-bottom-native-row-fixture.mjs`, `node tests/disabled-response-shortcuts-storage.mjs`, or `node --test tests/run-checks.test.js` | First inspect the fixture’s assertions. The native-row fixture exercises row selection, not complete controller teardown; the storage fixture is not a generic migration/cloud test. Choose by actual assertion coverage, not filename. |
| Validator/tool implementation and fixtures | `npm run test:validators`; `npm run test:shortcuts:contracts` when fast-runner/report contracts change | Their listed contracts and negative cases. Add a focused scenario only for an uncovered material defect. |
